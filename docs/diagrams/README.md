## Evidence boundary

The architecture artifacts contain repository evidence anchors and record the reviewed revision. The current independent check confirms the embedded source paths and line ranges at both the current working tree and revision `b4c63a86cdf9dab593d5556868f62b83953c304a`; exact content drift is reported separately, and a path/range check is not a behavioral proof. Documentation-only anchors in the architecture sources are `docs/02-ARCHITECTURE.md` (runtime architecture, eight ranges), `docs/06-DEPLOYMENT-AND-INFRASTRUCTURE.md:44-44` (production topology, the standalone raw-manifest example line), and `docs/08-OPERATIONS-RUNBOOK.md:89-99` (recorded in the index as current-tree documentation). The cryptographic architecture view carries no documentation anchor: it cites the `CryptographyOptions` doc-comment, which is byte-identical between the working tree and the pinned revision. Every other architecture anchor is a repository source or infrastructure path present at the pinned revision. The sequence, data-flow, workflow, and lifecycle artifacts are authored, untracked specifications whose compact source anchors were checked against that pinned revision; they are not themselves present in the pinned commit. These views express documented request, replay-state, nonce, binding, CI-gate, webhook, token-operation, and crypto-rotation paths; they do not prove runtime execution, conformance-suite results, production health, release publication, or Native AOT behavior. The request-flow and DPoP views distinguish pipeline/proof-validation stages from final HTTP outcomes; the DPoP view records that 2xx/3xx nonce rotation is best-effort because the `OnStarting` callback suppresses state-store failures. The current generated HTML outputs are present in the working tree, but their generation from the pinned revision is not independently provable because the sources and outputs are untracked and carry no embedded revision or source hash.

The architecture and production-topology HTML files embed the machine-readable `archify-source-evidence-data` payload. The five original sequence/data-flow/workflow/lifecycle HTML files include the shared viewer's source-badge code but no source-specific `archify-source-evidence-data` payload; their source anchors are carried in compact cards and in this index. The three added sequence/lifecycle/architecture views follow the same authored-artifact boundary for their source anchors, while the added cryptographic architecture HTML includes the architecture evidence payload for its checked source references. The release view's current generated HTML is regenerated from the untracked workflow source, not from the pinned commit. The source and output are authored artifacts and were absent from that commit. The diagrams deliberately exclude credential material and connection strings. The production topology's embedded documentation anchor is the single line `docs/06-DEPLOYMENT-AND-INFRASTRUCTURE.md:44`, which identifies the standalone raw-manifest example; the `:60-85` range quoted in the index below is a broader current-tree citation covering the Helm production overlay, HPA/PDB/network settings, and external boundaries, and is not an embedded anchor.

The three added views extend the index with distinct operational concerns: SSF/CAEP webhook processing, Keycloak refresh/exchange alternatives, and cryptographic rotation/reload. Their source anchors are current-tree documentation anchors plus the pinned-revision source ranges listed below; they are not claims of live external-service execution, conformance, or production rotation. The generated architecture payload's `verified` flag means only that the listed source paths and line ranges were checked at the pinned revision; it does not certify runtime behavior or semantic correctness. The cryptographic view distinguishes the reference-host JWT-bearer manager from the separately registered DI OIDC manager, shows opt-in TLS registration and disabled file watching, identifies the versioned AES-GCM key-ID envelope, and marks host-owned telemetry export. A refresh `400` containing `invalid_grant` sets the service's reuse flag and maps to the endpoint's 401 token-theft response; it is not independent proof of reuse, and the inspected branch does not call subject/session revocation or persist token-family state. Exchange has no equivalent flag. The outbound DPoP handler preserves a supplied proof or fills an absent one; generated proofs omit `ath`, and downstream sender-constrained acceptance is not established by this local gate. The refresh `clientIpHash` argument is not used by the service. The refresh service also treats a compatible parseable 2xx JSON object without `access_token` as success, which the endpoint can serialize as HTTP 200 with an empty access token; malformed JSON or incompatible token-field shapes fail the service path without setting the reuse flag. These are source-inspection boundaries, not live Keycloak or conformance results. The encryption contract makes lazy re-wrap persistence caller-owned; the inspected `src` and reference host contain no production persistence caller. The cache-cleanup source is a separate opt-in EF background service, not an AES-GCM cleanup path.
